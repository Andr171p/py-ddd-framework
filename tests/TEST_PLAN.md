# DDF DSL — план тестирования

**Статус:** Draft  
**Область:** `Condition`, `Group`, `Negation`, `Search`, `Expression`, валидация, компиляторы и использование DSL в репозиториях/API.  
**Цель:** подтвердить корректность семантики, безопасность пользовательского ввода, эквивалентность поддерживаемых операций между хранилищами и устойчивость сервиса под нагрузкой.

## 1. Принципы

- Тесты группируются **по уровню**, а не по признаку безопасности: `unit`, `integration`, `e2e`, `load`.
- Security-сценарии находятся в соответствующих наборах и дополнительно помечаются `security` (например, `@pytest.mark.security`; в нагрузочном инструменте — эквивалентным тегом).
- **Benchmarks не входят в план.** Здесь не сравниваются микросекунды разных реализаций `Union` и не создаются performance-regression benchmarks. В `load` оцениваются доступность, предельные режимы и потребление ресурсов реального сервиса.
- Проверяется **наблюдаемое поведение**, а не конкретный SQL/BSON, за исключением контрактов компилятора и проверки безопасной параметризации.
- Для каждой функции поддерживается набор позитивных, негативных и граничных случаев. Избыточно большие или потенциально опасные payload выполняются только в изолированном окружении.
- Отсутствующая функциональность не считается автоматически дефектом: кейс сначала связывается с поддерживаемым контрактом или помечается `planned`.

## 2. Контракт, который нужно зафиксировать до тестирования

1. **Форма AST:** публичный JSON не содержит `kind`; варианты распознаются по структурным признакам `field`, `filters`, `filter`, `query`. Если используется callable discriminator, он должен однозначно выбирать ветку и при разборе JSON, и при сериализации моделей.
2. **Операторы:** допустимые значения `ComparisonOperator` и `LogicOperator`; правила для `value` (обязательное, необязательное, запрещённое; скаляр или массив); смысл пустых групп и пустого `in`.
3. **NULL/missing:** различие SQL `NULL`, MongoDB `null` и отсутствующего поля; поведение `eq`, `ne`, `isNull`, `NOT` должно быть явно описано. Унифицировать только ту семантику, которую DDF действительно гарантирует.
4. **Поля:** разрешённые имена и вложенные пути, типы, поддерживаемые операторы; политика для неизвестных и запрещённых полей. Клиент не может ссылаться на произвольные ORM-атрибуты/колонки.
5. **Search:** является ли `Search` полноценным булевым узлом `Expression` или отдельной операцией поиска; какие хранилища поддерживают его семантику.
6. **Лимиты:** максимальный HTTP body, глубина AST, количество узлов, длина строк и размер массивов `in`; коды ошибок и момент применения лимитов.
7. **Обязательные ограничения:** организация, права доступа и soft-delete применяются вне пользовательского выражения и не могут быть отменены `OR`/`NOT`.

## 3. Unit tests

**Объект:** Pydantic-модели, десериализация, структурная/семантическая валидация, нормализация и независимые функции построения AST. Без сети и реальной БД.

| ID | Кейс | Идея и ожидаемый результат |
|---|---|---|
| U-01 | Распознавание узлов | `field` → `Condition`, `filters` → `Group`, `filter` → `Negation`, `query` → `Search`; публичный `kind` не нужен. |
| U-02 | Рекурсивный AST | Вложенные `AND`/`OR`/`NOT` корректно преобразуются в модели; структура и порядок сохраняются. |
| U-03 | Round-trip | `validate → serialize → validate` сохраняет структуру и семантику, включая alias `filter`. |
| U-04 | Неоднозначная структура `security` | Объект с несколькими маркерами (`field` + `filters`), лишними ключами или без маркера отклоняется. |
| U-05 | Обязательные поля | Отсутствие `op`, `field`, `filters`, `filter` и неверные типы приводят к контролируемой ошибке. |
| U-06 | Контракт операторов | Проверить допустимые операторы и формы значения: `in` требует массив, `gt` — совместимый скаляр, унарные операции — согласованный контракт `value`. |
| U-07 | Граничные значения | `null`, `0`, `false`, `""`, Unicode, UUID, даты и timezone, большие числа; несовместимые значения не проходят семантическую валидацию. |
| U-08 | Пустые конструкции | Пустая группа, группа из одного узла, пустой `in`, дубликаты в `in`: стабильное, задокументированное поведение. |
| U-09 | Булева логика | Проверить `AND`, `OR`, `NOT`, двойное отрицание и законы де Моргана с учётом выбранной семантики `NULL`. |
| U-10 | Имена полей `security` | Запрет неизвестных полей, недоступных вложенных путей, внутренних имён (`__dict__`, `metadata`) и оператороподобных имён. |
| U-11 | Опасные значения `security` | Значения с SQL/NoSQL-метасимволами трактуются как данные; объекты вида `{ "$ne": null }` не становятся операторами. |
| U-12 | Ограничение сложности `security` | AST выше максимума узлов/глубины, слишком большие строки/массивы отклоняются предсказуемо. |
| U-13 | Поведение при ошибках `security` | Нет неконтролируемых `RecursionError`, `KeyError`, `AttributeError`; ошибки не раскрывают секреты и детали инфраструктуры. |
| U-14 | Property-based AST | Hypothesis генерирует корректные рекурсивные деревья; round-trip, неизменяемость входа и логические инварианты сохраняются. |
| U-15 | Fuzzing `security` | Мутировать типы, маркеры, ключи, размеры и вложенность; валидатор либо принимает корректный AST, либо выдаёт ожидаемую ошибку. |
| U-16 | Детерминизм | Повторная валидация/нормализация одинаковых входов даёт эквивалентный результат; исходный объект не мутирует. |
| U-17 | `Search` | Пустой/длинный `query`, вложение в `Group` (если поддерживается), валидация текста и ограничений. |

**Генераторы:** фабрики валидных `Condition`/`Group`/`Negation`, рекурсивная стратегия Hypothesis с ограничением глубины и количества листьев; отдельно генератор невалидных payload.

## 4. Integration tests

**Объект:** настоящие PostgreSQL и MongoDB, SQLAlchemy/Mongo-компиляторы, репозитории и их взаимодействие. Использовать Testcontainers или Docker Compose, а не SQLite/mongomock вместо целевых СУБД.

| ID | Кейс | Идея и ожидаемый результат |
|---|---|---|
| I-01 | SQLAlchemy: основные операторы | `eq`, `ne`, диапазоны, `in`, null-проверки возвращают ожидаемые записи из PostgreSQL. |
| I-02 | MongoDB: основные операторы | Те же поддерживаемые операции на MongoDB возвращают ожидаемые записи. |
| I-03 | Композиция AST | Сложные `AND`/`OR`/`NOT` правильно транслируются в обе СУБД. |
| I-04 | Differential testing | Одинаковый датасет и выражение дают одинаковые наборы ID в рамках общего контракта двух хранилищ. |
| I-05 | `NULL` / missing | Проверить документы с `null`, отсутствующим полем и SQL `NULL`; расхождения фиксируются как особенности контракта или исправляются. |
| I-06 | Типы данных | Числа, даты с UTC-offset, UUID, Unicode; не происходит неожиданного приведения типов. |
| I-07 | SQL injection `security` | Payload вроде `' OR 1=1 --` в `value` не меняет структуру запроса и не расширяет выборку; значения параметризованы. |
| I-08 | NoSQL injection `security` | `$ne`, `$where`, `$expr`, вложенные dict/list в `value` не исполняются как пользовательские части Mongo-query. |
| I-09 | Инъекция в имя поля `security` | Неизвестные/системные атрибуты, произвольные dot-path и попытки подмены SQL-идентификаторов отклоняются. |
| I-10 | String matching `security` | `%`, `_`, `\`, кавычки и спецсимволы в `contains`/`ilike` имеют документированную семантику, не превращаются в неожиданные wildcard. |
| I-11 | Tenant isolation `security` | Для пользователя организации A ни `OR`, ни `NOT`, ни фильтр по `organization_id` не возвращают записи B. |
| I-12 | Доступ к полям `security` | Запрещённые поля нельзя фильтровать даже при наличии физической колонки; ограничения схемы проверяются до запроса. |
| I-13 | Soft-delete `security` | `NOT`, пустой фильтр или широкая `OR`-группа не возвращают удалённые записи, если политика это запрещает. |
| I-14 | Фильтр + сортировка + пагинация | Корректны `total`, страницы, стабильная сортировка и отсутствие пропусков/дубликатов на статичном датасете. |
| I-15 | Ошибки драйвера | Ошибки компиляции/передачи параметров и отмена запроса не оставляют испорченных транзакций/соединений. |
| I-16 | Конкурентность | Параллельное выполнение запросов с общим AST не вызывает мутаций состояния и смешивания параметров. |

**Тестовые данные:** две организации, разные роли, активные/удалённые записи, `null`, отсутствующие поля MongoDB, строки со спецсимволами, одинаковые значения сортировки. В I-04 сравнивать **множества ID**, а для пагинации — упорядоченные ID при фиксированном tie-breaker.

## 5. E2E tests

**Объект:** настоящий запущенный FastAPI-сервис, HTTP-запросы, аутентификация, репозитории и базы данных — без обхода транспортного слоя. Для сложной фильтрации — фактический endpoint приложения (например, `POST /resources/search`).

| ID | Кейс | Идея и ожидаемый результат |
|---|---|---|
| E-01 | Успешный поиск | Отправить вложенный JSON AST без `kind`; проверить статус, модель ответа и набор записей. |
| E-02 | Некорректный DSL | Неверные операторы/типы/маркеры дают установленный 4xx с понятной ошибкой, не 500. |
| E-03 | Ограничения AST `security` | Превышение глубины/размера `in`/количества узлов отклоняется до обращения к БД. |
| E-04 | Размер HTTP body `security` | Слишком большой запрос отклоняется на транспортном уровне (обычно 413) до дорогого парсинга. |
| E-05 | Межтенантный доступ `security` | Токен организации A + `OR`/`NOT` с ID организации B никогда не возвращает данные B. |
| E-06 | Авторизация полей `security` | Пользователь без нужных прав не может читать/фильтровать запрещённые данные, включая связанные поля. |
| E-07 | Утечка ошибок `security` | Ответы не содержат SQL, строк подключения, traceback, секретов и внутренней схемы БД. |
| E-08 | Пустая выборка и пагинация | Верные `items`, `total`, `page`/`size`, поведение при отсутствии результатов. |
| E-09 | Поиск и фильтрация | Если `Search` поддерживается публичным API, проверить его сочетание с фильтром и сортировкой. |
| E-10 | Восстановление после ошибок `security` | После серии невалидных/отклонённых запросов валидный запрос продолжает обслуживаться. |

## 6. Load tests

**Объект:** устойчивость настоящего API и хранилищ под длительной/параллельной нагрузкой. Это **не benchmarks**: не нужно искать «самый быстрый Union» или собирать микротайминги отдельных функций.

| ID | Кейс | Идея и ожидаемый результат |
|---|---|---|
| L-01 | Typical traffic | Смесь небольших реальных фильтров; стабильная доля успешных запросов, p95/p99, CPU/RAM и использование пула БД. |
| L-02 | Concurrent searches | Постепенно увеличивать число одновременных клиентов, наблюдать очереди, таймауты и восстановление. |
| L-03 | Near-limit AST `security` | Поток допустимых, но сложных деревьев; отсутствие неконтролируемого роста памяти/CPU. |
| L-04 | Invalid payload flood `security` | Много заведомо невалидных JSON/AST; отклонение без деградации обслуживания обычного клиента. |
| L-05 | Oversized requests `security` | Серия превышающих лимиты запросов; раннее отклонение, без раздувания памяти воркеров. |
| L-06 | Costly DB filters `security` | Низкоселективные `OR`, большие допустимые `in`, тяжёлые сортировки; действуют таймауты и ограничения ресурсов. |
| L-07 | Long-running soak | Длительная смесь валидных/невалидных запросов; нет устойчивого роста RSS, активных соединений и очередей. |
| L-08 | Recovery and cancellation `security` | После пика нагрузки и отключений клиентов сервис возвращается к штатному состоянию, без зависших запросов. |

**Наблюдаемые показатели:** RPS, p50/p95/p99 HTTP latency, 4xx/5xx, CPU, RSS, открытые соединения к БД, использование connection pool, таймауты, рестарты worker. Для нагрузочных тестов важнее отсутствие отказа и корректное ограничение ресурсов, чем отдельное абсолютное значение RPS.

**Критерии приёмки:** пороги p95/p99, допустимая доля ошибок, максимальный RSS и время восстановления фиксируются по окружению и бизнес-SLO *до* финального прогона. Ожидаемые 4xx от атакующих payload не считаются отказами. Тесты, намеренно провоцирующие истощение ресурсов, выполнять только в изолированном стенде.

## 7. Структура проекта

DSL лежит в тех же слоях, что и остальные тесты. Общие данные и каталоги — в `tests/helpers/dsl/`. E2E DSL не входит в realtime-compose: у него свой `tests/e2e/dsl/docker/`, по файлу на сервис.

```text
tests/
├── helpers/dsl/          датасет, выражения, SQL и Mongo каталоги
├── unit/dsl/             парсер и контракт значений, без Docker
├── integration/dsl/      PostgreSQL и MongoDB через testcontainers
├── e2e/dsl/              HTTP API, свой compose
│   └── docker/
│       ├── compose.yaml
│       ├── postgres.docker-compose.yml
│       └── api.docker-compose.yml
└── load/dsl/             Locust по уже запущенному e2e
```

`test_security.py` — просто тематическое имя файла **внутри соответствующего уровня**, а не отдельная категория тестов. Можно вместо этого размещать security-кейсы рядом с обычными в `test_validation.py` и `test_search_api.py`; главное — общий маркер `security`.

Для pytest зарегистрировать `security`, `integration`, `e2e`, `slow` в `pyproject.toml`, чтобы фильтровать прогоны (`pytest -m security`). Для Locust/k6 использовать аналогичные теги сценариев.

## 8. Инструменты и CI

- **Unit/property-based:** `pytest`, `hypothesis`, Pydantic `TypeAdapter`.
- **Integration:** `pytest-asyncio`, `testcontainers` либо Compose, реальные PostgreSQL и MongoDB.
- **E2E:** `httpx.AsyncClient` для ASGI-тестов и/или HTTP-клиент к отдельному запущенному сервису; для настоящего E2E предпочтительнее второй вариант.
- **Load:** `Locust` (Python) либо `k6`, метрики приложения и СУБД.
- **Нет отдельного JS/TS-клиента:** все уровни можно закрыть Python-инструментами.

| Запуск | Состав |
|---|---|
| Каждый PR | Unit, security-unit, короткие property-based tests; integration по возможностям CI |
| Merge в основную ветку | Полный integration и e2e (включая `security`) |
| Nightly/перед релизом | Расширенный fuzzing, длительные integration/e2e и контролируемые load-тесты |

## 9. Definition of Done

- Для каждого поддерживаемого оператора есть позитивный, негативный и граничный кейс.
- Любой недопустимый AST завершается контролируемым 4xx/validation error, а не необработанным исключением.
- SQL/NoSQL injection и обход tenant isolation не расширяют доступную выборку.
- SQLAlchemy и MongoDB согласованы по **документированной общей семантике**; исключения для `NULL`/missing явные.
- Ограничения сложности реально применяются до дорогостоящей работы; слишком большие HTTP body отклоняются раньше парсинга AST.
- Нагрузочные security-сценарии не приводят к устойчивому росту памяти, истощению соединений или длительной недоступности сервиса.
- Не существует отдельной директории `security/` или `benchmarks/`.

## 10. Порядок реализации

1. **Контракт и фикстуры:** операторы, `NULL`/missing, лимиты, два tenant, генераторы AST.
2. **Unit + Hypothesis:** структура Union, валидация, логика, invalid/fuzz cases, security-маркеры.
3. **Integration:** SQLAlchemy, MongoDB, differential testing, инъекции, изоляция организаций.
4. **E2E:** публичный API, ошибки, авторизация, ограничения размера запросов.
5. **Load:** typical traffic → near-limit → malicious traffic → recovery.

**Результат:** тесты подтверждают, что DSL одинаково предсказуем для разработчиков и безопасен в эксплуатации; сравнительные микробенчмарки реализаций остаются отдельной будущей задачей.
