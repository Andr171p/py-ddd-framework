# 0002. Использовать Pythonic-подход к DDD

**Статус:** Принято
**Дата:** 2026-09-17

## Контекст

Повторное применение DDD-подходов между Python-проектами часто приводит к переносу Java-церемоний: интерфейс на каждый класс, фабрики без логики, сервисы-обёртки и глубокие иерархии. Это увеличивает число файлов и скрывает правила, не повышая тестируемость.

При этом нужны реальные границы: домен не должен зависеть от FastAPI и SQLAlchemy, а инфраструктура должна заменяться в тестах.

## Решение

Использовать `dataclass` для доменных моделей, `Protocol` для портов, функции и небольшие классы для use case. Применять агрегаты, репозитории, Value Object и события только там, где они выражают бизнес-инвариант или границу инфраструктуры.

## Последствия

- API компактнее и естественнее для Python-разработчиков.
- Тесты доменных правил не требуют ORM или HTTP.
- Инкапсуляция поддерживается соглашением и методами поведения, а не принудительными getter/setter.
- Команде нужно дисциплинированно удерживать зависимости: отсутствие формальной абстрактной базы не отменяет архитектурную границу.

## Альтернативы

- **Классический enterprise DDD с ABС:** формальнее, но добавляет много шаблонного кода.
- **Active Record везде:** быстрее на старте, но смешивает схему хранения с бизнес-правилами.
- **Чистый CRUD без домена:** подходит для простых ресурсов, но плохо масштабируется с ростом инвариантов.
